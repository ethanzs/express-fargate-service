# api

An Express 5 + TypeScript JSON API, fronted by an ALB on ECS Fargate. It
authenticates callers with Microsoft Entra ID, serves items from Postgres with
a Valkey cache in front, and emits CloudWatch-ready logs and metrics.

For repo-wide setup (workspace install, docker compose, day-to-day commands),
see the [root README](../../README.md). Endpoint-by-endpoint reference:
[`docs/api.md`](../../docs/api.md) (generated by the `/api-docs` skill).

## Layout

```
src/
  app.ts               # createApp() — no listen(), so it's testable
  server.ts            # entrypoint: boot checks, listen, graceful shutdown
  config.ts            # env-driven config (12-factor; the only process.env reader)
  logger.ts            # pino logger (via the shared factory)
  db.ts                # pg pool + drizzle handle (lazy — no I/O at import)
  cache.ts             # iovalkey client + the Cache surface the repo uses
  repo/
    items.ts           # cache-aside reads, Postgres writes
  middleware/
    auth.ts            # requireAuth — Entra ID JWT validation
    validate.ts        # validate({ body, params, query }) — zod
    errorHandler.ts    # HttpError, ZodError→400, 404, central handler
  routes/
    health.ts          # GET /healthz (public)
    me.ts              # GET /api/me (returns the caller's claims)
    items.ts           # items REST resource (Postgres + Valkey)
test/                  # supertest + PGlite integration tests
```

## Authentication (Microsoft Entra ID / MSAL)

The frontend signs users in with MSAL and calls this API with the resulting
**access token** in `Authorization: Bearer <token>`. Every `/api/*` route runs
`requireAuth`, which verifies the token's signature (via the tenant JWKS),
issuer, audience, and expiry before the handler runs. `/healthz` stays public.

### One-time Entra ID setup

1. **Register the API** — create an App Registration for this service. Note the
   **Directory (tenant) ID** and **Application (client) ID**.
2. **Expose an API** — under _Expose an API_, set the Application ID URI
   (e.g. `api://<client-id>`) and add a scope (e.g. `access_as_user`).
3. **Frontend app** — its MSAL config requests that scope; the access token it
   receives is what this API validates.

### Calling a protected route

```bash
curl localhost:3000/api/me -H "Authorization: Bearer <access-token>"
```

`req.auth` holds the verified claims (`oid`, `name`, `roles`, …). The `roles`
claim is already captured for the planned admin/role-based access — enforcement
will layer on top of `requireAuth` later.

> **Token version gotcha:** the defaults assume **v2.0** access tokens. If your
> app registration still issues v1.0 tokens (`accessTokenAcceptedVersion` is not
> `2` in the manifest), the issuer is `https://sts.windows.net/<tenant-id>/` —
> set `AZURE_AD_ISSUER` accordingly, or flip the manifest to v2.0.

## Configuration

Set these locally in `.env` (copy `.env.example`), on Fargate in the task
definition / Secrets Manager. The server **fails fast on boot in production**
if a required value is missing; in dev it logs a warning (auth-less `/api`
requests return 401, store-less item reads fail).

| Variable                                                      | Required      | Notes                                                                                                |
| ------------------------------------------------------------- | ------------- | ---------------------------------------------------------------------------------------------------- |
| `AZURE_TENANT_ID`                                             | yes           | Directory (tenant) ID                                                                                |
| `AZURE_CLIENT_ID`                                             | yes           | This API's Application (client) ID                                                                   |
| `AZURE_AD_AUDIENCE`                                           | yes           | Expected `aud` — client id or `api://<client-id>`                                                    |
| `DATABASE_URL`                                                | password mode | Postgres connection string (local dev / compose)                                                     |
| `DB_AUTH` / `DB_HOST` / `DB_PORT` / `DB_NAME` / `DB_USER`     | iam mode      | AWS: `DB_AUTH=iam` + endpoint/user — per-connection RDS auth tokens via the task role, no credential |
| `VALKEY_URL`                                                  | yes           | Valkey endpoint (`rediss://` with in-transit encryption)                                             |
| `CACHE_TTL_SECONDS`                                           | no            | TTL on keys written back on a cache miss (default 3600)                                              |
| `AZURE_AD_INSTANCE` / `AZURE_AD_ISSUER` / `AZURE_AD_JWKS_URI` | no            | Auth overrides (sovereign clouds / v1.0 tokens)                                                      |
| `CORS_ORIGINS`                                                | no            | Comma-separated SPA origins; empty denies cross-origin                                               |
| `PORT` / `HOST` / `LOG_LEVEL` / `SERVICE_NAME`                | no            | Standard service knobs (see `.env.example`)                                                          |
| `JSON_BODY_LIMIT`                                             | no            | Max request body (default `100kb` → 413 beyond)                                                      |
| `KEEP_ALIVE_TIMEOUT_MS` / `HEADERS_TIMEOUT_MS`                | no            | Must exceed the ALB idle timeout (defaults 65s/66s)                                                  |

## Data access (Postgres + Valkey, cache-aside)

Items live in **Postgres (system of record)** with **Valkey as the cache** in
front of it (`src/repo/items.ts`; the drizzle table, types, and `items:<id>`
key format come from `@app/shared`):

- **The hydrator bulk write-throughs** both stores on its schedule (rows +
  TTL'd cache keys).
- **`GET /api/items/:id`** tries the cache first; on a miss (expired TTL,
  missing key) it reads Postgres and **writes the key back with a fresh TTL**
  (`CACHE_TTL_SECONDS`), so subsequent reads hit the cache again. Any cache
  problem — down, garbage value, failed write-back — degrades to Postgres,
  never errors. Listing reads Postgres directly.
- **`POST /api/items`** inserts into Postgres with a generated identity id
  (the hydrator bumps the sequence past its seeded ids); the first read caches
  it.

`/healthz` stays dependency-free so a slow datastore can't cause health-check
restart loops (`/readyz` readiness gating is a roadmap item).

## Validation & errors

Request input is validated with [zod](https://zod.dev) via the
`validate({ body, params, query })` middleware (`src/middleware/validate.ts`).
Request schemas live next to their route; domain shapes shared with the
hydrator (like `Item`) live in `@app/shared` and the route schemas derive from
them (`ItemSchema.pick(…)`/`.omit(…)`). The sanitized body (trimmed/coerced) is
written back to `req.body`.

A failed validation returns **400** with field-level detail:

```http
POST /api/items   { }
→ 400
{ "error": "Validation failed", "details": [{ "path": "name", "message": "..." }] }
```

The central error handler (`src/middleware/errorHandler.ts`) also reads
`status`/`statusCode` off library errors, so a malformed JSON body returns 400 and
an oversized body (over `JSON_BODY_LIMIT`) returns 413 — not a 500.

> Express 5 notes: rejected promises from async handlers land in the error
> handler automatically (handlers can just `throw`), and `req.query` is a
> **read-only getter** — the middleware validates it in place.

## Observability

Structured JSON logs via the shared `createLogger()` factory, plus
`pino-http` request logging (`/healthz` excluded — the ALB polls it
constantly). On top of the shared redaction base list, this service scrubs
`req.headers.authorization` (the bearer token), cookies, and
`x-api-key`; add new paths in `src/logger.ts`.

One EMF metrics line per completed request (`src/middleware/metrics.ts`) —
CloudWatch extracts real metrics from the log stream, no extra IAM. Namespace
`ExpressFargateService`, dimensioned by `service`/`env` + `route`/`statusClass`:

| Metric                 | Unit         | Use                                                   |
| ---------------------- | ------------ | ----------------------------------------------------- |
| `RequestCount`         | Count        | throughput, request rate                              |
| `RequestLatency`       | Milliseconds | p50/p90/p99 latency (CloudWatch computes percentiles) |
| `HttpServerErrorCount` | Count        | 5xx rate, error alarms                                |

> **Cardinality matters.** Dimensions use the matched **route template**
> (`GET /api/items/:id`) and a coarse **status class** — never the raw URL, an
> id, or a user — so the number of metric streams stays bounded.

### Request identity & auditing

- After auth, `requireAuth` binds the **pseudonymous** actor to the request
  logger (`userId` = Entra `oid`, `tenantId` = `tid`). Name/email are
  deliberately **not** logged — the immutable `oid` is the stable key, and
  keeping PII out of logs avoids retention/erasure (GDPR) headaches.
- Each request gets a **correlation id** (`reqId`) from the ALB's
  `X-Amzn-Trace-Id` header (or `X-Request-Id`), falling back to a UUID.
- **Audit events** (security-relevant actions) go through `recordAudit()` in
  `src/audit.ts` — a separate stream tagged `log_type:"audit"`, pinned to
  `info` so it's never suppressed by `LOG_LEVEL`. This is the seam for the
  planned admin/RBAC features.

## Running & testing

```bash
# from code/ (see the root README for full local-dev setup)
npm run dev -w api        # hot reload via tsx, loads api/.env
npm test -w api           # supertest (auth/error paths) + PGlite repo tests
```

Tests need no Docker and no Azure config: auth tests assert the 401 paths
(the JWKS set is built lazily, so `createApp()` does no network I/O), and the
repository tests run the real migrations + SQL against in-memory Postgres
(PGlite), reusing the hydrator's migration history.
